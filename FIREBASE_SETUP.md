# Firebase setup for Golden Eagle Marketplace

The app's product discussions, community-post likes, comments and comment likes, vendor-following feed, community photo/video posts, profiles, timed quiz, reaction store, in-app notifications, and Golden Chat use Firebase Authentication, Cloud Firestore, Cloud Storage, and Cloud Functions. Golden Chat supports private Buyer–Vendor conversations with paid text, photo, and voice-note messages. Community post and comment voice recordings are visible to visitors; verified signed-in users can like posts, comment, like other members' comments, and post voice-only comments or attach voice notes to text. Comment authors cannot like their own comments. A Like on a community post or product spends one earned Like credit, is recorded once per member and item, and cannot be removed or refunded; counts are visible in post feeds and on Vendor profiles. Existing free post Likes and legacy product Like records remain intact and do not get charged retroactively. Comment Likes remain separate and free. Product reactions are limited to one per account per product; Hate behavior remains credit-based. Quiz rewards and purchased Hate/chat credits are credited or debited by callable Cloud Functions, never directly by the browser. Vendors can spend 10 Golden Chat coins to send an in-stock alert to their followers; followers see it in the Notifications menu. The side menu also has a Quiz & reaction store entry; Followers and Following remain under My profile. Product-discussion and community-comment voice recordings have no time limit and are capped at 25 MB per upload. Following the vendor feed, profile editing, presence, and dark-mode behavior remain as described below.

## One-time Firebase Console setup

1. In project `golden-eagle-marketplace`, enable **Authentication → Sign-in method → Email/Password** and **Phone** if those methods will be used.
2. Add `goldenphoneshop.github.io` under **Authentication → Settings → Authorized domains**. For local testing, add `localhost`.
3. Create a Cloud Firestore database and a Cloud Storage bucket in the project.
4. Enable billing for the project before deploying Cloud Functions. Firestore, Storage, Functions, and audio downloads can incur charges. Set a budget alert in Google Cloud Billing and monitor Firebase usage.
5. To upload and display profile photos without public download-token URLs, configure CORS on the Storage bucket. The configuration must include the website's exact origin and the upload methods (`POST` and `PUT`) as well as read methods. Install the Google Cloud CLI, authenticate it with an account that can administer the bucket, then run:

   ```powershell
   gcloud storage buckets update gs://golden-eagle-marketplace.firebasestorage.app --cors-file=storage.cors.json
   ```

   `storage.cors.json` allows profile-photo uploads and reads from the GitHub Pages website and local HTTP test servers on ports 5000, 5500, and 5501. If the site uses a different domain or local port, add that exact origin to the file before applying it. Opening the HTML directly as a `file://` URL is not supported for Firebase; serve it over HTTP or test on the hosted HTTPS site. Reapply CORS after changing the file.

Email registration saves the selected display name and Buyer/Vendor role to the member's own Firestore profile before sending the verification email. Firestore rules therefore allow a signed-in account to create only its own validated profile document before email verification; profile reads, edits, chat, and other member features still require a verified account. After verifying, sign in again to load the saved profile and role on any device. Phone sign-in requires Phone Authentication, an authorized HTTPS/localhost domain, and working reCAPTCHA/SMS settings.

Verified members can see public profile totals for permanent Likes received on community posts and products, lifetime Likes earned from completed quizzes, currently available quiz Likes, and follower/following counts. Follower and Following lists are visible to verified members by default. In App Settings, the account owner can independently make either list private; privacy hides the list contents, not its public count, and never prevents the owner from viewing their own list. These settings are enforced by Firestore rules. The totals are returned by the `getPublicProfileStats` callable, so deploy the current Cloud Functions and Firestore rules together with the updated marketplace page.

Public Like totals update live on marketplace product cards, product details, vendor profile listings, and community posts. Counts come from the server-managed `productDiscussionStats` and `communityPostStats` documents; a dash means the count is loading and "Unavailable" indicates a read error. Publish the updated marketplace page to make these displays available.

Firebase Authentication sessions are scoped to the website origin. A sign-in on a local `file://` page does not automatically sign the same browser into `https://goldenphoneshop.github.io`; sign in once on each origin. Both origins can use the same Firebase account and shared Firestore data, but their browser sign-in sessions are separate. New email registrations are signed out until the email is verified; sign in on the website after verification.

After updating the authentication flow, deploy the revised Firestore rules with `firebase deploy --only firestore:rules` and publish the current workspace `Markertplace.html`. Its auth-state listener is registered independently of the page's other startup work and updates the signed-in navigation; the deployed page must include this listener or successful authentication may not appear in the header. Confirm Email/Password is enabled, `goldenphoneshop.github.io` is in Firebase Authentication's authorized domains, and browser cookies/site storage are allowed.

## Configure Flutterwave before taking payments

The store uses fixed prices in NGN: N500 for 5 hates and N1,000 for one daily pack of 5 extra quiz plays. Every account receives 2 free reward plays daily; completing either awards 10 likes regardless of score. The five paid extra plays do not award likes. Unlimited practice is free and does not award likes. Buying hates does not require playing a quiz. New Love purchases and product Love reactions are disabled; historical Love credits and reaction records are retained and are not deleted. The page fetches a public NGN/USD rate only to show an approximate dollar equivalent; Flutterwave is charged the fixed NGN amount. A phone-only account is prompted for an email address for its payment receipt.

1. Enable Flutterwave checkout for your merchant account and configure your **settlement bank account** in the Flutterwave dashboard. Flutterwave settles funds according to the merchant account's dashboard settings. Vendor bank transfers use the separately funded Flutterwave payout balance and the launch-controlled payout functions described below.
2. Set the Flutterwave API secret key and the webhook secret hash as Firebase Functions secrets. Do not put either secret in HTML, source control, or a chat message:

   ```powershell
   firebase functions:secrets:set FLUTTERWAVE_SECRET_KEY
   firebase functions:secrets:set FLUTTERWAVE_WEBHOOK_HASH
   ```

3. After deploying functions, copy the HTTPS URL printed for `flutterwaveWalletWebhook` into Flutterwave's webhook settings. Use the same webhook secret hash stored as `FLUTTERWAVE_WEBHOOK_HASH`.
4. Checkout redirects to `https://goldenphoneshop.github.io/Markertplace.html`; update `PAYMENT_REDIRECT_URL` in `functions/index.js` if the published page uses another URL.

The backend creates each checkout from a server-side price table, verifies the transaction with Flutterwave, checks currency, amount, reference, and receipt email, and credits the wallet only once. The webhook and browser return both use that verification path; a browser redirect alone never grants credits. Secret configuration, deployment, and the merchant settlement account must be completed before checkout can work.

Golden Chat coin packs use the same verified Flutterwave flow: 12 coins for ₦350, 50 for ₦1,500, and 350 for ₦7,500 (300 + 50 bonus). The server credits coins to the signed-in member's wallet only after verified payment. The Golden Chat page and coin store show the available balance from that wallet in real time; the balance is also refreshed from Firestore after payment verification. When Flutterwave returns to the marketplace with a transaction reference, the signed-in page verifies the transaction before clearing the return details. If a completed purchase is still missing, the member can use **Coins missing? Verify a purchase** with the `tx_ref` and transaction ID from their Flutterwave receipt. The server verifies ownership, amount, currency, and payment status before crediting; it cannot be used to add coins manually. There is no six-month Chat subscription.

The in-app **Buy Golden Chat coins** links in the marketplace hero and side menu open the purchase packs directly for Buyers and Vendors. The **How Golden Coins work** guide explains the purchase and chat flow. The separate `golden_chat_architecture.html` and `golden_coin_utility_blueprint.html` are design/demo references, not trusted payment or wallet code. Server-verified coin packs, chat message costs, product boosts, Verified Dealer Badges, stock-alert broadcasts, referral rewards, and daily check-in rewards are implemented.

Verified Buyers and Vendors receive 5 Golden Coins once per West Africa Time day when opening the signed-in marketplace. `claimDailyCheckIn` credits the server-controlled wallet transactionally; failed claims are reported and can be retried by reopening the app. The day resets at midnight WAT (23:00 UTC).

Vendors can create store-only voucher codes; administrators can create store-specific or platform-wide codes. Vendors must explicitly opt in to each platform-wide code after reviewing its terms. Codes expire 30 days after creation, are funded from the discounted vendor product price, and may be used once per buyer; they do not consume Golden Coins. The backend quotes and revalidates the discount, calculates the 7.5% protection fee on the discounted price, reserves the code with the stock, and marks it used on verified payment. Expired or failed checkout reservations release the code; a late payment that conflicts with a later reservation is sent to the automatic refund path. Orders retain the original price, discount, and code. Vouchers may not reduce a product below NGN 100. Deploy the updated Cloud Functions, Firestore rules, and marketplace page together; real Flutterwave voucher payments and late-payment refunds require end-to-end testing.

Product cards and a cart containing one unit of one listed product can preview the escrow fee. Real payment, webhook delivery, and vendor withdrawals require end-to-end verification; automated administrator refunds remain test-only. The fee for new checkouts is 7.5% of the product price, rounded to the nearest kobo (half a kobo rounds up). Existing payments retain their recorded amounts for verification and settlement. Publish `functions/escrow-fee.js` along with the marketplace page and deploy the functions together so their calculations match. No payment or funds protection is provided by the preview.

New checkout requires a fulfillment choice: home/location delivery costs NGN 2,750 and requires street address, city/LGA, state, and phone (optional landmark); pickup is free at one of the three configured Lagos stations. The selected location and fee are validated and priced by the server, saved with the pending payment and order, and sent to Flutterwave as payment metadata. Home-delivery details are visible to the buyer, vendor, administrators, and Flutterwave. This records the preference; it does not automatically book a courier or reserve space at a station. The checkout minimum product price is NGN 100 so a product-only refund meets the provider minimum. When an order is released, the vendor ledger receives the product price and the marketplace ledger receives both the protection and fulfillment fees.

The administrator refund policy refunds the full payment before dispatch; after dispatch it refunds only the product price and retains the remaining fees once the refund is confirmed. Marking a pickup order ready for pickup counts as dispatch. Existing orders without fulfillment details retain their original full-refund behavior. Live refunds require manual initiation and verification as described below. Deploy `functions/escrow-fulfillment.js` with both the page and Cloud Functions, and test the payment and refund flow with Flutterwave before relying on it.

The test checkout asks Flutterwave for a 15-minute checkout session and rejects totals below NGN 100, Flutterwave's documented minimum refund. It reserves stock transactionally and schedules expired reservation release and payment lookup every five minutes. A provider-verified failed payment attempt also releases the reservation; Flutterwave may still allow the buyer to retry that checkout. A later successful payment attempts to reserve the item again; if it is unavailable, the server initiates a full refund. The scheduled job and late-payment refund path have only mocked tests, not provider end-to-end verification.

Server-side order transitions and client write restrictions support vendor shipment, buyer disputes, and release after buyer confirmation or an administrator's release decision; released product amounts and platform fees are recorded in separate server-only ledgers. Checkout, payment verification and scheduled recovery use the live wallet `FLUTTERWAVE_SECRET_KEY` in the `golden-eagle-marketplace` project and use the production marketplace redirect. In other projects they use the test `FLW_SECRET_KEY` and require a separate Firebase project explicitly named by `ESCROW_TEST_PROJECT_ID` and a separate HTTPS site in `ESCROW_TEST_REDIRECT_URL`. Both secrets are bound to those functions and must exist in the deployed Firebase project. The `flutterwaveEscrowTestWebhook` additionally requires `FLW_SECRET_HASH` and remains restricted to the test project. Checkout buttons and buyer/vendor order management are present in the marketplace page. Live vendor payouts require the launch flag below; automated administrator refunds remain test-only and the dashboard verifies separately initiated manual refunds. The production webhook URL and hash are configured, but real Flutterwave event delivery has not been verified; do not replace the production wallet webhook with the test webhook. Uncertain refunds require manual reconciliation and cannot be retried automatically. These changes have only mocked tests and must not be advertised as a complete protection system without end-to-end integration, reconciliation, and provider testing.

Vendor cash is stored only in `vendorPayoutBalances/{uid}.availableKobo`; released product proceeds, after buyer-paid protection and fulfillment fees, are credited once. Spendable Golden Chat coins remain in `quizWallets/{uid}.coins` and cannot fund withdrawals. Both documents are readable only by their owner and writable only by trusted server code; no balance migration is needed. The vendor profile settings show both balances, a bank selector, verified account name, payout quote, and up to 25 payout records (the history is not guaranteed to be the newest 25).

Vendors choose the whole-naira amount sent to their bank (minimum NGN 2,000). The quote adds the NGN 500 base fee, a commission of 1.5% below NGN 10,000, 2.5% below NGN 50,000, 3.5% below NGN 200,000, or 5% thereafter, and Flutterwave's quoted transfer fee rounded up to kobo. The server verifies the vendor and bank, re-quotes, reserves the total cash debit transactionally, and creates a uniquely referenced transfer. A verified success records platform fees once. A provider-verified `FAILED` transfer restores the full reserved cash once; timeouts, missing IDs, mismatches and other uncertain statuses remain reserved for support reconciliation. Never retry a failed or uncertain transfer manually in Flutterwave: a later provider retry after cash has been restored could pay the vendor twice. Investigate reversals or conflicting later provider statuses manually. Flutterwave charges on failed transfers, if any, must be reconciled separately.

Live payouts are **off by default**. Deploy the changed functions while off and publish the marketplace and admin pages; configure the production `flutterwaveWalletWebhook` and verify actual provider webhook delivery. Before launch, test the bank list, account verification, fee quote, successful and failed transfers, concurrent requests, webhook recovery, and support reconciliation in a separate test project with a Flutterwave test key. Confirm merchant KYC, API transfer permissions, IP requirements, and sufficient NGN payout-wallet funding with Flutterwave. The wallet ledger does not prove that funds are segregated or available at the provider. Do not enable live payouts until operational reconciliation and real-provider testing are complete.

The functions bind existing `FLUTTERWAVE_SECRET_KEY` and `FLW_SECRET_KEY`; the production webhook also needs `FLUTTERWAVE_WEBHOOK_HASH`. Set any missing secret interactively using `firebase.cmd functions:secrets:set SECRET_NAME --project golden-eagle-marketplace`; never place secret values in dotenv files or source control. To deploy with the launch gate off:

```powershell
firebase.cmd deploy --only functions:getVendorPayoutBanks,functions:getVendorBankAccount,functions:saveVendorBankAccount,functions:getVendorPayoutQuote,functions:requestVendorWithdrawal,functions:checkVendorWithdrawal,functions:adminCheckVendorWithdrawal,functions:reconcileEscrowWithdrawal,functions:flutterwaveWalletWebhook,functions:askGoldenAi --project golden-eagle-marketplace
```

For the separate test project, configure `ESCROW_TEST_PROJECT_ID`, its test redirect and Flutterwave test secrets as described above, and deploy the payout functions plus `flutterwaveEscrowTestWebhook` to that project. Because the payout functions bind both key secrets, the test project also needs its own `FLUTTERWAVE_SECRET_KEY`; use a test key there, never the production key. Configure `FLW_SECRET_HASH` for the test webhook.

Only after the checks above, add the non-secret line `ESCROW_LIVE_PAYOUTS_ENABLED=true` once to `functions/.env.golden-eagle-marketplace`, then run the same deployment command again. Set it to `false` and redeploy to stop new payouts; existing payouts remain checkable. All listed functions, including `askGoldenAi`, must be redeployed together when changing the flag. Publishing the HTML files requires the usual GitHub Pages workflow. The payout functions, UI and actual Flutterwave responses have not been tested end-to-end with Flutterwave.

### Administrator dashboard

Publish `admin.html` and deploy the updated Cloud Functions before use. Sign in with a verified Firebase account carrying the `admin: true` custom claim; use the trusted Admin SDK procedure in the quiz section below. The server independently enforces this claim. Configure the admin origin as a Firebase Authentication authorized domain and enable the desired sign-in providers. The page targets the production Firebase project; for test payout support, publish a separate test copy configured with the test project's Firebase web configuration and authorized domain. Never put service-account credentials or Flutterwave secrets in either page.

Before using metrics, ensure Firestore has a collection-scope composite index on `escrowOrders` with `status` ascending and `totalPaid` ascending; build it in the Firebase console without removing existing indexes. The dashboard's fulfillment counts use equality filters on `fulfillment.method` and `status` and normally use Firestore's automatic index merging. If the project disables automatic indexes or reports a missing index, configure the required indexes before use.

The recorded active total includes held, shipped, disputed, and awaiting-refund orders at their recorded gross totals. It is not a verified bank balance or segregated escrow balance, and pending partial refunds are not deducted. Fulfillment counts cover recorded delivery and pickup methods by order status; legacy orders without a method are excluded. Check-ins and the corresponding five-coin awards count wallets whose latest check-in is today in WAT, not coin spending/redemptions; historical daily totals are unavailable. These are current snapshots, not audited financial reports.

To refund a disputed order, select **Prepare manual refund** before doing anything at the provider. The function locks the order against release and shows the Flutterwave transaction ID and exact amount. Initiate that amount manually in the correct Flutterwave merchant account, then enter its existing refund ID in the dashboard. The server checks the provider ID, transaction, amount and status before updating the order; pending refunds remain locked, and final refunds record any retained fees once. If a provider request or outcome is uncertain, do not issue another refund: investigate and verify the existing provider record. If it cannot be identified or does not match, leave the order locked and contact support.

Payouts are submitted by vendors, not approved by an administrator. The dashboard can check an existing payout or reconcile an uncertain payout using its existing Flutterwave transfer ID, after enforcing the recorded NGN 2,000 minimum. It never initiates a transfer. The dashboard also exposes the existing test-only refund check/reconciliation path; automatic production refund issues require manual investigation. Unmatched provider records remain reserved for support review. Manual refunds, provider responses, dashboard flows and payout reconciliation have not been verified end-to-end with Flutterwave.

The test escrow webhook routes `charge.completed`, `transfer.completed`, and `refund.completed` events, as well as Flutterwave's documented unenveloped V3 refund payload, after checking `FLW_SECRET_HASH`. It independently checks the provider record before updating financial state. Transfer and refund webhooks received before their provider IDs are saved can attach the ID after verifying the provider record; absent or failed webhooks still require reconciliation. The existing wallet webhook routes escrow events automatically in `golden-eagle-marketplace` and can enable the shared path elsewhere with `ESCROW_LIVE_WEBHOOK_ENABLED=true`. Production checkout and the shared webhook use the same `FLUTTERWAVE_SECRET_KEY`; verify that it is the live key for the intended merchant, and configure that merchant's dashboard to send events to `flutterwaveWalletWebhook` using `FLUTTERWAVE_WEBHOOK_HASH`. If the shared path is enabled in a test project, its wallet key must belong to the same test merchant account as `FLW_SECRET_KEY`. Verify actual refund payloads and delivery, shared wallet/escrow routing, and account configuration end-to-end before using production checkout.

## Golden AI assistant

The assistant requires verified sign-in and provides guidance only. It has no account, order, payment, or editing tools; it cannot look up a particular user's order. Public product questions use an unauthenticated Firestore REST request restricted to title, category, price and stock, not an Admin SDK query. It scans at most 500 products and says when the catalog scan is incomplete. Public product data is not sent to Gemini. Marketplace checkout, refund, voucher and order guidance is handled locally; other questions may be sent to Gemini with Google Search grounding. Users must not enter personal information, credentials, order numbers, code or payment details. The filter blocks common sensitive patterns but cannot identify every sensitive message; prompts and external searches are processed by Google. Do not log prompts or provider payloads. AI answers and safety filters are not infallible, and external search can incur charges.

Before deploying, create a **dedicated** service account for `askGoldenAi` with no Firestore, Storage, account-management, or application-data write permissions. Verify that neither project-level nor inherited IAM grants give it those permissions. Grant it only access to the `GEMINI_API_KEY` secret and other strictly necessary platform runtime permissions. The Firestore public-read rules on `products` must remain enabled for catalog lookup. The callable keeps a hashed caller ID and request counter only in instance memory for a best-effort limit; the limit is per instance and is not a distributed spending cap. Set provider quotas and billing alerts, and consider App Check or infrastructure-level rate limiting before production use.

Set the Gemini API key securely with `firebase functions:secrets:set GEMINI_API_KEY --project golden-eagle-marketplace` (enter it at the prompt; do not put it in source control). Set the non-secret `GOLDEN_AI_SERVICE_ACCOUNT` parameter to the dedicated service account email, for example `golden-ai-assistant@golden-eagle-marketplace.iam.gserviceaccount.com`, when Firebase prompts during deployment or in `functions/.env.golden-eagle-marketplace`. Grant that account Secret Manager Secret Accessor on **only** the `GEMINI_API_KEY` secret, and ensure the deployment identity can act as the service account. Deploy `askGoldenAi` using `firebase deploy --only functions:askGoldenAi --project golden-eagle-marketplace`, then publish `Markertplace.html`. Use the corresponding project and dedicated identity in other environments. Verify IAM, actual provider responses, search suggestions, rate controls and the published page before relying on the assistant. The Google Search grounding requirements and pricing are described at https://ai.google.dev/gemini-api/docs/generate-content/google-search.

## Golden Chat

- Golden Chat supports private conversations between any two verified marketplace members (Buyer and/or Vendor), including Buyer-to-Buyer and Vendor-to-Vendor chats. A general conversation may be started from any other member's profile. Product-linked conversations remain Buyer–Vendor enquiries started from a Vendor listing and display its current recorded stock; stock is not a reservation or guarantee. Starting a new conversation requires the sender to have at least 1 available chat coin, but does not deduct it. Reopening an existing conversation does not require a balance.
- The sender pays 1 coin per text message, 2 per photo, 4 per video clip, or 3 per voice note, regardless of Buyer/Vendor roles. On successfully delivered Buyer-to-Vendor text messages and voice notes only, half the sender's charge is credited to the Vendor's spendable wallet (0.5 text coin or 1.5 voice-note coins); photos and videos do not earn a share. The Buyer still pays the full price. Other role combinations do not earn a share, duplicate sends do not credit it again, and the receiving participant is not charged. Text deductions and message creation happen together in a server-side transaction; photo/video/voice coins are reserved before upload and finalized only when a message is created. Failed or abandoned media reservations are refunded, and a scheduled Cloud Function cleans up expired uploads. The browser cannot write messages or adjust balances directly. Photos are limited to 5 MB, video clips to 50 MB, and voice notes to 25 MB.
- Swipe a text message to the right or use its Reply button to quote it in a new message. The server verifies that the referenced message belongs to the same conversation and saves a short preview; replies use the normal message or media coin charge. In Golden Chat, Find people keeps the searchable followers/following list beside the conversation so members can continue scrolling. Deploy `sendGoldenChatMessage` before publishing the updated marketplace page.
- A Vendor can spend 5 Golden Chat coins to boost an owned product for 24 hours; another purchase extends the existing expiry. `boostProductListing` verifies the Vendor, ownership, and balance and atomically updates the wallet and listing. The `boostedUntil` field is server-managed; clients cannot create or change it.
- A Vendor can purchase a Verified Dealer Badge for 24 coins for one UTC calendar month and may opt in to automatic monthly renewal in profile settings. `purchaseVerifiedDealerBadge` checks role and balance and atomically deducts coins, stores the private profile expiry, and updates the public read-only `verifiedDealers/{uid}` status. `setVerifiedDealerAutoRenew` changes the server-controlled preference; `processVerifiedDealerBadgeRenewals` charges 24 coins and extends the badge in one transaction at expiry. If funds are insufficient, auto-renew is paused and the badge expires. After topping up, the Vendor must re-enable it; re-enabling a paused, expired badge securely charges 24 coins and restarts the month. Renewal records and all wallet, badge, and renewal-setting writes are server-only. The badge tooltip states: “Purchase grants a marketplace badge but is not independent identity/business verification.”
- A Vendor can spend 10 Golden Chat coins to alert their followers about an owned product that currently has stock. `sendStockAlertToFollowers` checks the verified Vendor role, listing ownership, stock, followers, and wallet balance in one transaction, then queues a server-managed broadcast. `deliverStockAlertNotifications` creates one in-app notification per follower and records delivery status. Clients cannot create notifications or broadcasts; recipients can only read their own notifications and mark each as read once.
- The Notifications menu shows server-created alerts for new followers, chat messages, missed calls, escrow status changes, payout status, wallet changes and purchases, and profile/settings changes. Notification text does not include message contents or financial details. The latest 50 are loaded initially; use **Load older notifications** for earlier entries. The unread badge counts only the currently loaded entries. New Vendor listings generate a free, near-real-time in-app notification for that Vendor's followers; the separate paid follower stock alert is unchanged. Recipients are determined from the followers present when the event is processed. Listings can currently be created only by Vendors.
- These notifications start with events occurring after deployment; they do not backfill old account activity. The scheduled missed-call worker starts tracking calls created after its first run, marks unanswered ringing calls ended after at least 60 seconds, and does not change older call records. The existing call-history display can still show older missed calls. Scheduled processing and Firestore reads/writes and retained notifications incur usage and may require billing. Clients cannot read or change the server-only call-worker settings. Retries reuse notification IDs and preserve read status.
- If the earlier digest functions were deployed, explicitly delete `queueNewProductDigest` and `deliverDailyProductDigest` using the Firebase CLI before deploying these changes, to stop the old scheduled broadcasts; their stored records are not automatically deleted. Deploy the updated Firestore rules and indexes with `firebase.cmd deploy --only "firestore:rules,firestore:indexes"`, and wait for the new call index to become ready. Then deploy `firebase.cmd deploy --only "functions:notifyNewFollower,functions:notifyGoldenChatMessage,functions:notifyMissedCall,functions:notifyEscrowOrder,functions:notifyVendorWithdrawal,functions:notifyWalletPurchase,functions:notifyWalletUpdate,functions:notifyAccountUpdate,functions:notifyNewVendorProduct,functions:expireUnansweredCalls,functions:sendGoldenChatMessage"` before publishing `Markertplace.html`. No new secrets are required. Verify delivery between test accounts and verify the schedule and index in Firebase; in-app notifications are not push notifications and may be delayed when a function is retried.
- Buyers and Vendors can copy their unique referral link in My profile > Edit profile. A new member opens the link and registers; the server must attach the referral within 24 hours of the Firebase account's creation. If attribution fails, the same browser retains it for retry at the next sign-in or via **Refresh referral status** in profile settings. After email/phone verification and completing the chat-ready profile (including an actual profile photo and a business description for Vendors), the server awards 10 spendable Golden Chat coins to the referrer and 5 to the new member. Both wallet credits and the single per-new-member award record are committed in one transaction; retried requests and profile events cannot award twice. Self-referral to the same account is blocked, but verification alone cannot prevent one person creating multiple accounts; monitor the program for abuse. Firestore referral records and wallets are server-only. Deploy `getReferralInfo`, `recordReferralSignup`, `completeReferralQualification`, `processReferralAttribution`, `processReferralProfileCompletion`, and the updated rules before publishing the marketplace page.
- Chat media is stored at private participant-only paths. The page loads it using authenticated Storage reads, so configure the Storage CORS origins before testing media. Coin purchases require the Flutterwave setup above.
- Golden Chat voice and video calls are free and do not deduct coins. Deploy the Firestore rules and call index (`firebase.cmd deploy --only "firestore:rules,firestore:indexes"`), wait for the index to finish building, and publish both `Markertplace.html` and `golden-calls.js` together. Both verified participants must have the site open over HTTPS and allow microphone/camera access. Calls use browser WebRTC with Google's STUN server only; some networks cannot connect without a TURN relay. Peer and STUN provider can receive network metadata such as IP addresses. Firestore retains the call documents, SDP and ICE candidates until an administrator deletes them; no automatic signaling-data cleanup is configured. Test voice and video calls between two accounts, including denied permissions and hang-up, before announcing availability. Scheduled cleanup for chat media reservations requires Cloud Scheduler; Firebase provisions its schedule when the function deploys, and Cloud billing must be enabled.
- The full-screen call view offers audio output selection when the browser supports it and an optional 1.5× audio boost. Browser output selection does not guarantee a phone's loudspeaker can be selected; use the device's sound controls if it is unavailable. Each conversation shows recent incoming and outgoing call records, including declined or missed calls, alongside messages without charging coins. An unanswered ringing record is shown as missed after 60 seconds, including if the caller disconnects without updating it; this does not add a push notification or chat unread badge. Answered means the recipient answered, not necessarily that the peers connected. Deploy the two call-history indexes in `firestore.indexes.json` and wait for them to build before publishing the updated page and script.

## Quiz and reaction-store behavior

- Each quiz selects up to 5 questions the member has not seen in the current rotation of enabled questions. If fewer than 5 unseen questions remain, the quiz uses that smaller number; a new rotation begins only after the enabled bank has been seen. Each question has four shuffled options and a separate 30-second deadline enforced by the server. Answers are recorded one question at a time, and the correct answer is shown after each submitted question. The first 2 free reward plays per UTC day award 10 likes each when completed, regardless of score. A verified N1,000 purchase adds 5 more daily plays, but these additional plays do not award likes. Every started reward play consumes a daily play, including one that is abandoned. Exiting an active quiz asks for confirmation; confirmed exits are marked abandoned and cannot be submitted for rewards. Free practice is unlimited and never awards likes. Daily limits reset at 00:00 UTC. No monthly quiz subscription is required.
- If the enabled-question query is still empty after seeding (for example, an administrator has disabled every question), the quiz start function returns a non-blocking `no-enabled-questions` state without creating an attempt or consuming a reward play. The page explains that an administrator must enable a question before quiz play is available; this does not block Golden Chat messages or coin purchases.
- On the first quiz start, the trusted Cloud Function transactionally seeds one enabled GSM-basics question into `quizQuestions` only if that collection has no documents. This makes a new installation playable while preserving any questions an administrator has already added or intentionally disabled.
- Correct answers are returned only after the corresponding question is submitted; answers to current and future questions are not exposed beforehand. The admin editor is shown only when the signed-in Firebase ID token has the `admin: true` custom claim. Grant this claim only to a trusted administrator using the Firebase Admin SDK in a controlled environment; do not make a client-side role field authoritative. For example, from a trusted environment already initialized for this Firebase project with Admin SDK credentials:

  ```js
  const { getAuth } = require("firebase-admin/auth");
  (async () => {
    const user = await getAuth().getUserByEmail("admin@example.com");
    await getAuth().setCustomUserClaims(user.uid, {
      ...(user.customClaims || {}),
      admin: true
    });
  })().catch(console.error);
  ```

  Replace the example email with the intended administrator account. Never place service-account credentials in the website or commit them. Sign out and back in after changing the claim. An admin can add, edit, disable, and delete questions in App Settings. Add at least one enabled question before playing; quizzes contain up to 5 questions when enough enabled questions are available. Correct-answer indices are stored in Firestore and are not included in the public page or function source.
- Wallet, daily-play usage, attempt, purchase, and product-reaction writes are Cloud Function-only. Community-post Like records, Like-credit deductions, and counts are updated together in a server transaction. Product Likes debit the same wallet transactionally with the saved reaction; a Cloud Function maintains product Like/Hate totals. Firestore rules allow members to read public counts and only their own community-post Like record. Firestore rules allow account owners to read their balance but block client-side writes to balances and quiz usage. Notification content and broadcast records are server-created; a recipient may only set the read timestamp on their own notification. A missing or undeployed function means rewards and reactions will fail explicitly rather than being credited locally.
- Product Like reactions are permanent and cannot be removed or refunded. The existing Hate toggle remains refundable when removed. Historical reactions are preserved; an old Like record does not consume any new credit.

## Deploy the rules and Cloud Functions

Install Node.js 20 or later and the Firebase CLI on the deployment computer. From the project root:

```powershell
npm install --prefix functions
firebase login
firebase use golden-eagle-marketplace
firebase deploy --only firestore:rules,storage,functions
```

The app uses **Cloud Firestore** for structured marketplace data: member profiles, product listings, community posts and comments, follows, quiz questions and attempts, wallets, and Golden Chat messages. **Cloud Storage** holds uploaded profile photos, product/community photos and videos, discussion voice recordings, and private Golden Chat media. Quiz questions and rewards are not files, so they belong in Firestore; the browser cannot write quiz answers, correct-answer keys, wallet balances, or chat charges directly. Cloud Functions performs those trusted operations.

The rules restrict vendor product creation and editing to a verified account whose Firebase user profile has the `Vendor` role. The role is created once for the signed-in account and cannot be changed by later profile updates. Verified users can read marketplace profiles; profile photos are read through authenticated Storage access rather than stored public URLs. Profile photos are limited to 5 MB and JPG, PNG, WebP, or GIF. Users can update their display name, photo, location, gender, age range, description, `allowMediaDownloads`, and their own `followersPrivate`/`followingPrivate` preferences, but not their account role. Verified Buyers and Vendors can publish community photo/video posts and reshare existing community posts. The app permits any number of photos per community post or product listing (5 MB per photo) and one video. Buyers can upload community videos up to 500 MB with no client-side duration cap; vendors can upload community videos up to 50 MB and the browser checks a 10-second duration limit. Product videos remain limited to 50 MB and a browser-checked 10 seconds. Firestore documents have a 1 MiB maximum size, so extremely large photo URL lists may exceed the platform's document limit despite no app-level count cap. Storage rules enforce role-specific video size limits, but cannot inspect duration; vendor duration checks are a client-side usability limit that can be bypassed by a modified client. Community media and post records are publicly readable. A new community-post Like costs one wallet Like credit, is stored per member, cannot be removed, and updates the publicly readable count in the same transaction. Existing free Likes remain uncharged. Community comment voice notes are limited to 25 MB and are removed from Storage when their comment is deleted. The download setting controls the app's download button and is checked before it starts a download; it cannot prevent people from saving media through other browser/device methods or using a previously copied public Firebase media URL. Buyers and vendors with verified sign-in can read and comment on public product discussions. Product Like/Hate reactions are changed only through `applyProductReaction`; Likes spend one credit and are permanent, while Hate totals continue to be maintained by a Cloud Function. Verified members can search for Buyers and Vendors by exact email address or by prefixes of a display name, location, role, or public business/about information. Email addresses are used only for matching and are never returned or shown. Search is server-mediated and rate-limited; directory and search-limit documents are not client-readable. A member directory entry is created when a profile changes or when its owner signs in after the feature is deployed. Buyers and Vendors can follow each other; reciprocal following/follower records are written together. Vendor product listings are also shown on each Vendor profile and remain available in the public marketplace. The `presence/{userId}/sessions/{sessionId}` rules allow public reads of presence state only; only the verified account owner can update or delete their own session records.

Golden Chat requires a completed member profile and verified sign-in. Conversation creation, Buyer/Vendor eligibility, message reads, coin purchases, and coin deductions are enforced by Cloud Functions, Firestore rules, and Storage rules. Unread-message counts are incremented in the same server transaction as a successful send and are cleared by the `markGoldenChatRead` callable when the recipient opens that conversation. The count appears beside Conversations, on each conversation, and beside Golden Chat in the menu. After deploying, test separate verified Buyer and Vendor accounts plus Buyer-to-Buyer and Vendor-to-Vendor conversations; verify that an account with no available coins cannot start a new conversation, that existing conversations can still be reopened, that text/photo/video/voice-note sends update unread counts without charging twice, and that opening the conversation clears the recipient's count. Existing messages sent before unread tracking was deployed do not have reliable read markers and cannot be backfilled accurately. Real-time calls remain unavailable until a provider is configured; do not advertise or charge for them before end-to-end testing.

## Vendor product photo and video uploads

The vendor listing form accepts any number of uploaded photos and one uploaded video. Photos must be JPG, PNG, WebP, or GIF and are limited to 5 MB each. Product videos must be MP4, WebM, or MOV, no larger than 50 MB, and the page checks their duration is at most 10 seconds before upload and again before publishing. Firebase Storage rules restrict uploads to verified Vendor accounts, restrict media MIME types and size, and make the resulting product media readable for public marketplace listings. They do not inspect video duration: the 10-second duration check runs in the browser, so it is a usability limit, not a server-side media-transcoding guarantee.

Deploy `storage.rules` along with the page changes. Product media is stored at `products/{vendorUid}/{productId}/{fileName}` and the resulting Firebase download URLs are saved with the listing. Buyer/vendor community media is stored at `community-media/{uid}/{postId}/{fileName}` and referenced by public download URLs in `communityPosts`. Community comments are stored at `communityPosts/{postId}/comments/{commentId}`; verified users can create comments, and only the author can delete their own comment. A verified Buyer or Vendor can like or unlike another member's comment. Likes are stored per user under `communityPosts/{postId}/comments/{commentId}/likes/{uid}`; the `toggleCommunityCommentLike` Cloud Function atomically records the user's like and updates the comment's `likesCount`. Users can read only their own like record, and client-side writes to like records and counts are denied by Firestore rules. Buyer community video uploads may be up to 500 MB; vendor community and product videos remain limited to 50 MB. Existing starter products and older listings may still display their prior images; the new vendor-post flow no longer accepts external image URLs.

Replies on community posts and product discussions use the existing comments collection with an optional `parentCommentId`. Verified members can reply to existing comments, including other replies, using the same text and voice options as comments. Firestore rules require the parent to exist in the same post or discussion; authors can still delete only their own comments. Replies remain visible if their parent is deleted or outside the most recent 50 community comments or 100 product comments, with a label explaining the parent is unavailable. Publish the page and deploy the updated Firestore rules together to enable replies.

## Voice recordings and deletion

Voice recording requires microphone permission and an HTTPS page (or localhost). Community and product comments and replies may contain text, a voice note, or both. Recordings stop when the 25 MB limit is reached. Deleting your own comment triggers a Cloud Function that removes its audio file from Storage. Voice players hide the browser's download option where supported and suppress their context menu, but this cannot prevent a listener from saving or recording audio: playback requires delivering the audio to their device, and comment voice files are publicly readable. Public audio playback may incur Storage egress charges.

If deployment fails, check that Firestore and Storage are enabled, billing is active for Functions, the selected Firebase project is correct, and the Firebase CLI is logged in to an account with deployment permission.
